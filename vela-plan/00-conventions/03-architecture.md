# 03 — Архитектура

## 1. Слои

```
┌──────────────────────────────────────────────────────────────┐
│ C/Overlay   палитра, аннотации, настройки, онбординг         │  top-most
├──────────────────────────────────────────────────────────────┤
│ B/UI        холст, виджеты, док, стеклянные панели           │  над иконками
├──────────────────────────────────────────────────────────────┤
│ A/Scene     фото/видео/2D/3D/игра                            │  под иконками
├──────────────────────────────────────────────────────────────┤
│ WorkerW / рабочий стол Windows                               │
└──────────────────────────────────────────────────────────────┘
        ▲                                    ▲
        │ Rust core (один процесс)           │
        └── окна, БД, планировщик, захват ───┘
```

## 2. Процессная модель

- Один процесс. WebView2 для каждой поверхности — отдельный рендер-процесс
  (управляется самим WebView2, не нами).
- Rust-ядро: главный поток (окна, Win32-сообщения) + пул tokio для БД и сети +
  отдельный поток планировщика (cron).
- Общение Rust ↔ UI: Tauri IPC. Тяжёлые потоки данных (кадры, скриншоты) — не
  через IPC, а через общую папку кэша + путь в сообщении.

## 3. Владение состоянием

| Данные | Владелец | Копии |
|---|---|---|
| Раскладка, элементы, настройки | SQLite (`state.db`) | кэш в Zustand, read-through |
| Режим ввода, зум/пан | Zustand (поверхность B) | — |
| Позиция/размер окон, z-order | Rust | — |
| Состояние планировщика | Rust (поток cron) | события в UI |
| Буфер обмена, история | Rust | снапшот в UI по запросу |
| Тема | SQLite + `prefers-color-scheme` | CSS-переменные |

Правило: UI никогда не пишет в SQLite напрямую — только через IPC-команду,
которая валидирует и возвращает новое состояние.

## 4. Потоки данных: три типовых пути

1. **Перетаскивание виджета.** Pointer-событие → Zustand (транзиентно, 60 Гц) →
   по `pointerup` IPC `layout.apply_patch` → SQLite → событие `layout.changed`
   (для других мониторов).
2. **Смена профиля.** UI → IPC `profile.activate` → Rust останавливает таймеры,
   меняет сцену (команда в A), отправляет новую раскладку в B → ack.
3. **Скриншот.** Хоткей в Rust → захват через `Windows.Graphics.Capture` →
   PNG в кэш → IPC `capture.ready {path, rect}` → поверхность C открывает
   аннотатор с путём.

## 5. Обработка ошибок

- Rust: `thiserror` в библиотеке, `anyhow` на границе приложения. Ошибка
  логируется с ID задачи, если это ожидаемый сбой платформы.
- UI: `ErrorBoundary` на каждый виджет — падение одного модуля не роняет холст;
  виджет заменяется плашкой «модуль остановлен» с кнопкой перезапуска.
- Платформенные деградации: перечислены в `07-risks.md`, у каждой — видимое
  пользователю состояние, а не только запись в лог.

## 6. Производительность: правила

- Любая анимация идёт через `requestAnimationFrame`-цикл, который **останавливается**
  при отсутствии изменений и при `document.hidden`.
- Сцена A останавливает рендер при: fullscreen-приложении в фокусе, профиле
  «экономия», работе от батареи ниже 25 %, отсутствии видимого монитора.
- Стекло пересчитывается только при изменении сцены или геометрии панели,
  не каждый кадр.

## 7. Безопасность

- IPC-команды не принимают произвольные пути: только из списка разрешённых корней.
- Виджеты сторонних разработчиков (если включаются) — только в изолированном
  iframe со своим origin и без доступа к privileged API.
- Приватные данные (история буфера, OCR-текст) — в отдельном файле БД с
  опциональным шифрованием через DPAPI.
